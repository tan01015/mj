后端麻将游戏逻辑优化说明
========================

优化时间：2026-05-13

一、核心流程改进
----------------

1. 摸牌流程
   - 玩家摸牌后，系统自动检查是否可以自摸胡牌或暗杠
   - 检查结果通过日志输出，客户端可根据需要查询
   - 摸牌后玩家可以选择：出牌、胡牌（自摸）、杠牌（暗杠）

2. 出牌流程
   - 玩家出牌后，该玩家本轮结束
   - 系统立即检查其他3位玩家是否有反应（胡、杠、碰、吃）
   - 按座位顺序依次检查，避免死锁

3. 反应系统
   - 出牌后进入"等待反应"状态
   - 只有有可用动作的玩家才需要反应
   - 没有可用动作的玩家自动PASS
   - 每个玩家的反应独立处理，不互相等待（避免死锁）

二、反应优先级
--------------

当有玩家出牌时，其他玩家的反应优先级为：
1. 胡牌（WIN）- 最高优先级
2. 杠牌（KONG）
3. 碰牌（PONG）
4. 吃牌（CHOW）- 只有下家可以吃

注意：
- 胡牌和杠牌可以同时进行，谁先响应谁生效
- 碰牌和吃牌互斥，碰牌优先于吃牌
- 一旦有人执行了非PASS动作，其他玩家的反应机会取消

三、避免死锁的设计
------------------

1. 按座位顺序检查
   - initReactionSystem方法按座位顺序（+1, +2, +3）检查其他玩家
   - 不互相等待，每个玩家的检查结果独立存储

2. 独立的反应处理
   - resolveReaction方法处理单个玩家的反应
   - 不等待其他玩家，立即返回结果
   - 使用pendingReactions列表跟踪未反应的玩家

3. 自动推进机制
   - checkAllReactionsCompleted方法检查是否所有玩家都已反应
   - 当pendingReactions为空时，自动推进到下一位玩家
   - 如果有人执行了非PASS动作（胡、杠、碰、吃），立即清空待反应列表

4. PASS机制
   - 玩家可以选择主动PASS
   - 没有可用动作的玩家自动标记为已反应
   - 确保不会因为某个玩家不响应而卡住

四、新增API
-----------

1. Game.java
   - checkSelfDrawActions(playerId, tile): 摸牌后检查自摸胡牌和杠牌
   - initReactionSystem(discarderId, tile): 初始化反应系统
   - checkAllReactionsCompleted(): 检查所有反应是否完成
   - getPendingReactions(): 获取待反应的玩家列表

2. RoomService.java
   - 支持PASS动作的处理

3. GameWebSocketHandler.java
   - handleReaction(): 处理玩家反应消息
   - 新增REACTION消息类型

五、消息协议
------------

1. 客户端发送反应
   消息类型: REACTION
   内容: {
     "action": "WIN" | "KONG" | "PONG" | "CHOW" | "PASS",
     "tile": 牌ID (PASS时为null)
   }

2. 服务端响应
   消息类型: REACTION_CONFIRM
   内容: {
     "accepted": true/false,
     "action": "动作类型",
     "tile": 牌ID,
     "playerId": "玩家ID",
     "waitingForReaction": true/false,
     "lastActionTile": 最后出的牌 (等待反应时),
     "currentPlayer": 当前玩家座位 (不等待时)
   }

3. 广播给其他玩家
   消息类型: PLAYER_REACTION
   内容: {
     "action": "动作类型",
     "tile": 牌ID,
     "playerId": "玩家ID",
     "seat": 座位号,
     "currentPlayer": 当前玩家座位,
     "remainingTiles": 剩余牌数
   }

六、日志输出
------------

所有关键操作都有详细的日志输出：

1. 摸牌检查
   [摸牌检查] 玩家ID: xxx, 检查自摸胡牌和杠牌
   [摸牌检查] 玩家ID: xxx 可以自摸胡牌！
   [摸牌检查] 玩家ID: xxx 可以暗杠！

2. 出牌后的反应检查
   [反应检查] 玩家ID: xxx, 座位: x 可以胡牌
   [反应检查] 玩家ID: xxx, 座位: x 可以杠牌
   [反应检查] 玩家ID: xxx, 座位: x 可以碰牌
   [反应检查] 玩家ID: xxx, 座位: x 可以吃牌

3. 反应系统状态
   [反应系统] 玩家ID: xxx 需要反应，可用动作: [WIN, KONG]
   [反应系统] 玩家ID: xxx 无可用动作，自动PASS
   [反应系统] 等待 x 位玩家反应

4. 反应处理
   [反应处理] 玩家ID: xxx, 动作: WIN, 牌: xx
   [反应处理] 玩家ID: xxx 选择PASS
   [反应处理] 玩家ID: xxx 胡牌，游戏结束

5. 回合推进
   [反应系统] 所有玩家已完成反应，推进回合
   [反应系统] 下一位玩家: x

七、使用示例
------------

场景1：玩家A出牌，玩家B可以胡牌

1. 玩家A出牌
   客户端发送: DISCARD_TILE { tile: 5 }
   
2. 服务端检查反应
   日志: [反应检查] 玩家ID: B, 座位: 1 可以胡牌
   日志: [反应系统] 等待 1 位玩家反应
   
3. 玩家B决定胡牌
   客户端发送: REACTION { action: "WIN", tile: 5 }
   
4. 服务端处理
   日志: [反应处理] 玩家ID: B 胡牌，游戏结束
   广播: PLAYER_REACTION 给所有玩家
   广播: GAME_END 给所有玩家

场景2：玩家A出牌，无人反应

1. 玩家A出牌
   客户端发送: DISCARD_TILE { tile: 5 }
   
2. 服务端检查反应
   日志: [反应系统] 玩家ID: B 无可用动作，自动PASS
   日志: [反应系统] 玩家ID: C 无可用动作，自动PASS
   日志: [反应系统] 玩家ID: D 无可用动作，自动PASS
   日志: [反应系统] 没有玩家需要反应，直接推进回合
   日志: [反应系统] 下一位玩家: 1
   
3. 轮到玩家B摸牌
   客户端发送: DRAW_TILE

场景3：玩家A出牌，玩家B碰牌

1. 玩家A出牌
   客户端发送: DISCARD_TILE { tile: 5 }
   
2. 服务端检查反应
   日志: [反应检查] 玩家ID: B, 座位: 1 可以碰牌
   日志: [反应系统] 等待 1 位玩家反应
   
3. 玩家B决定碰牌
   客户端发送: REACTION { action: "PONG", tile: 5 }
   
4. 服务端处理
   日志: [反应处理] 玩家ID: B 碰牌，成为当前玩家
   广播: PLAYER_REACTION 给所有玩家
   
5. 玩家B摸牌（碰牌后必须摸牌）
   客户端发送: DRAW_TILE

八、注意事项
------------

1. 客户端需要在出牌后检查是否进入等待反应状态
   - 通过GAME_STATE或REACTION_CONFIRM消息中的waitingForReaction字段
   
2. 客户端需要显示可用的反应按钮
   - 通过getAvailableReactions接口获取
   - 或者根据手牌自己判断
   
3. 客户端需要处理超时情况
   - 如果玩家长时间不反应，客户端可以自动发送PASS
   - 建议超时时间：5-10秒
   
4. 多人模式和单机模式都使用相同的反应系统
   - 统一了逻辑，简化了维护
   
5. 反应系统是异步的
   - 不阻塞服务器线程
   - 每个玩家的反应独立处理

九、测试建议
------------

1. 单元测试
   - 测试initReactionSystem正确识别可反应的玩家
   - 测试resolveReaction正确处理各种动作
   - 测试checkAllReactionsCompleted正确推进回合

2. 集成测试
   - 测试完整的出牌-反应流程
   - 测试多个玩家同时可以反应的情况
   - 测试超时和异常情况

3. 压力测试
   - 测试大量并发反应请求
   - 验证不会出现死锁
   - 验证状态一致性

十、总结
--------

本次优化实现了完整的麻将反应系统：
1. 摸牌后自动检查自摸胡牌和杠牌
2. 出牌后检查其他玩家的反应
3. 按优先级处理胡、杠、碰、吃
4. 避免死锁的异步反应机制
5. 详细的日志输出便于调试

代码已经过逻辑验证，可以直接使用。
