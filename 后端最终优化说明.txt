麻将后端逻辑最终优化说明
========================

优化时间：2026-05-13

一、符合真实麻将规则的核心流程
------------------------------

1. 摸牌阶段
   - 当前玩家从牌墙摸一张牌
   - 摸牌后手牌变为14张
   - 系统自动检查：
     * 是否可以自摸胡牌（14张牌满足胡牌条件）
     * 是否可以暗杠（手中有4张相同的牌）
     * 是否可以加杠（之前碰过，现在摸到第4张）
   - 检查结果通过日志输出，客户端可以查询
   - 玩家可以选择：出牌、自摸胡牌、暗杠、加杠

2. 出牌阶段
   - 玩家从14张牌中选择一张打出
   - 出牌后手牌恢复为13张
   - 出牌者本轮结束
   - 系统立即检查其他3位玩家的反应

3. 反应阶段（出牌后）
   按逆时针顺序检查（下家、对家、上家）：
   
   a) 胡牌（点炮）
      - 任何位置的玩家都可以胡牌
      - 优先级最高
      - 有人胡牌则游戏立即结束
   
   b) 杠牌（明杠）
      - 任何位置的玩家都可以明杠
      - 需要手中有3张相同的牌
      - 优先级次于胡牌
   
   c) 碰牌
      - 任何位置的玩家都可以碰牌
      - 需要手中有2张相同的牌
      - 优先级次于杠牌
   
   d) 吃牌
      - 只有下家可以吃牌
      - 需要手中有能组成顺子的2张牌
      - 优先级最低

4. 反应处理
   - 每个玩家的反应独立处理，不互相等待（避免死锁）
   - 一旦有人执行非PASS动作（胡/杠/碰/吃）：
     * 清空所有待反应列表
     * 执行动作的玩家成为当前玩家
     * 该玩家需要摸牌（继续游戏）
   - 如果所有人都PASS：
     * 推进到出牌者的下家
     * 下家摸牌继续游戏

二、关键改进点
--------------

1. 正确的回合推进
   - 出牌后如果没有人反应，推进到出牌者的下家（不是currentPlayer+1）
   - 碰/吃/杠后，执行者成为当前玩家，需要摸牌
   - 确保游戏流程符合真实麻将

2. 吃牌限制
   - 只有下家可以吃牌（i==1的判断）
   - 对家和上家不能吃牌
   - 符合真实麻将规则

3. 杠牌的三种类型
   - 明杠：别人打出，手中有3张
   - 暗杠：自己摸到第4张，手中有4张
   - 加杠：之前碰过，现在摸到第4张
   - 每种类型的处理逻辑不同

4. 胡牌的两种类型
   - 自摸：自己摸到的牌胡牌（isSelfDraw=true）
   - 点炮：别人打出的牌胡牌（isSelfDraw=false）
   - 计分不同

5. 避免死锁的设计
   - 按座位顺序依次检查，不互相等待
   - 每个玩家的反应独立处理
   - 使用pendingReactions列表跟踪
   - 自动推进机制确保不会卡住

四、API接口说明
---------------

1. Game.java 新增方法

   checkSelfDrawActions(playerId, tile)
   - 摸牌后自动调用
   - 检查自摸胡牌、暗杠、加杠的可能性
   - 通过日志输出结果

   initReactionSystem(discarderId, tile)
   - 出牌后自动调用
   - 按逆时针顺序检查其他3位玩家
   - 初始化待反应列表

   resolveReaction(playerId, action, tile)
   - 处理玩家的反应动作
   - 支持：WIN, KONG, PONG, CHOW, PASS
   - 返回是否成功

   getPendingReactions()
   - 获取待反应的玩家列表
   - 用于客户端显示

   getStateSummary()
   - 获取当前游戏状态摘要
   - 包含所有关键信息
   - 用于调试和显示

2. WebSocket 消息类型

   REACTION（客户端发送）
   {
     "type": "REACTION",
     "action": "WIN" | "KONG" | "PONG" | "CHOW" | "PASS",
     "tile": 牌ID (PASS时为null)
   }

   REACTION_CONFIRM（服务端响应）
   {
     "type": "REACTION_CONFIRM",
     "accepted": true/false,
     "action": "动作类型",
     "tile": 牌ID,
     "playerId": "玩家ID",
     "waitingForReaction": true/false,
     "lastActionTile": 最后出的牌,
     "currentPlayer": 当前玩家座位
   }

   PLAYER_REACTION（广播给所有玩家）
   {
     "type": "PLAYER_REACTION",
     "action": "动作类型",
     "tile": 牌ID,
     "playerId": "玩家ID",
     "seat": 座位号,
     "currentPlayer": 当前玩家座位,
     "remainingTiles": 剩余牌数
   }

五、完整游戏流程示例
--------------------

假设4位玩家：A(座位0), B(座位1), C(座位2), D(座位3)

 round 1:
 1. A摸牌 -> 检查自摸/杠 -> A出牌5
 2. 检查反应：B(下家)可吃，C(对家)可碰，D(上家)无动作
 3. C选择碰牌 -> C成为当前玩家 -> C摸牌
 4. C摸牌 -> 检查自摸/杠 -> C出牌8
 5. 检查反应：D(下家)无，A(对家)无，B(上家)无
 6. 无人反应 -> 推进到D -> D摸牌
 7. D摸牌 -> 检查自摸/杠 -> D出牌2
 8. 检查反应：A(下家)可胡 -> A选择胡牌 -> 游戏结束

六、注意事项
------------

1. 客户端实现建议
   - 出牌后，检查waitingForReaction字段
   - 如果为true，显示反应按钮（胡/杠/碰/吃/PASS）
   - 根据getAvailableReactions或自己判断显示可用动作
   - 设置超时时间（5-10秒），超时自动发送PASS

2. 多人模式 vs 单机模式
   - 两者使用相同的反应系统
   - 单机模式中，AI也需要通过REACTION接口响应
   - 统一了逻辑，简化维护

3. 并发安全
   - 所有操作都是同步的，不会出现竞态条件
   - pendingReactions使用ArrayList，单线程访问
   - 不需要额外的锁机制

4. 性能考虑
   - 反应检查是O(n)复杂度，n=3（其他玩家数）
   - 胡牌判定可能需要递归，但手牌最多14张，性能可接受
   - 日志输出可能影响性能，生产环境可调整级别
